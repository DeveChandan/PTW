# PTW procedure and application gap review

Review date: 28 September 2026

The current application implements creation of a SAP permit request, not the complete field permit lifecycle. The site procedure also contains conflicting instructions and form labels. Resolve those document conflicts with the procedure owner before turning them into automatic authorization rules.

## Scope and evidence

- Reviewed the supplied 79-page PDF, HSE/SAF/P/01, revision 03 dated 01 April 2026, focusing on process clauses, responsibilities, approval and validity tables, and the annexed permit form HSE/SAF/02 Rev-08 on pages 55–58. Page references below are the PDF's printed page numbers. Key tables and form pages were visually checked against rendered pages.
- Inspected the current React source, SAP request serializer, role registry, types, and lifecycle API helpers. This establishes what this checkout implements; it does not establish what people currently do at the site or what a deployed SAP backend enforces.
- `PTW Format revision 1.docx` is a Microsoft rights-managed encrypted container. Its contents could not be read. The embedded permit form in the PDF is a separate source and must not be assumed to match that DOCX. An accessible export from an authorized user is needed to complete the three-way comparison.
- No application code or source documents were changed. No live permit was created, approved, issued, suspended, or closed. Recommendations below concern alignment with the supplied procedure, not independent validation of its safety thresholds.

## Current process implemented in the application

SAP sign-in and role-based module access → select a real maintenance order or notification → enter general details and a single permit category → add crew → add PPE and free-text safety checks → enter hazards and controls → enter an isolation plan → review and POST a permit request to SAP in `CRTD` status.

Evidence: [application routing](D:/App/PTW/src/App.tsx:82), [creation steps](D:/App/PTW/src/features/permits/PermitCreateModule.tsx:473), [creation validation](D:/App/PTW/src/core/api/modules/permitCreate.validation.ts:36).

Only Permit Create has a functional module screen. All other selected modules resolve to `ComingSoonModule`. Having a TypeScript interface or an API helper does not mean its process is available to users. The creation serializer deliberately excludes gas signatures, approvals, audit entries, attachments, and renewals. That is reasonable for a request, but those records need later workflows before field authorization.

The existing checks correctly require a work reference, crew matching the headcount, hazard/control descriptions, valid chronological dates, and a returned SAP permit number. A successful request is not permission to start work.

## Suggested target process

1. **Plan and classify:** use the approved routine/non-routine activity list; identify job, location, equipment, relevant work categories, affected districts and special approvals. Record authorized emergency/deviation paths separately.
2. **Prepare the request and JSA:** joint site visit, job steps, hazards, controls, responsible persons, crew, tools, PPE, plans and supporting references.
3. **Verify the site:** applicable preparations, isolation/zero-energy evidence, specialist clearances, competent personnel and fresh gas tests.
4. **Collect the approved signing sequence:** issuer certification, applicable isolation/clearance signatures, required I/II/III approvals, acceptance and operator clearance according to the corrected matrix. The rigging sequence conflict must be settled before fixing a universal order.
5. **Release and execute:** completed toolbox attendance, clear authorized start/expiry, accessible permit and supporting documents, monitoring and gas retests.
6. **Revalidate or suspend:** apply shift/personnel changes, expiry, changed conditions and emergency rules. Record why work stopped; require appropriate revalidation before restart.
7. **Close and restore:** acceptance of completion and housekeeping, operator verification, issuer sign-off, then controlled restoration where applicable. Keep trial energization distinct from final closure.
8. **Retain and audit:** immutable record of documents, revisions, signatures, readings, actions and reasons; implement the stated retention and audit requirements.

This is a proposed implementation structure, not an approved replacement for the procedure.

## Recommended order of work

1. **Document owner and HSE:** resolve D01–D10 first, approve the consolidated role/time/activity matrix, and identify the controlled revision of the separate format DOCX. Obtain the referenced individual standards where they govern conflicts.
2. **Frontend and SAP teams:** correct the safety-category length bug; remove assumed calibration success; align API fields/actions and version metadata. Keep draft/request behavior separate from field authorization.
3. **Workflow implementation:** deliver issuer/acceptor/operator/approver, isolation, gas-test, renewal, suspension and closure workflows, with mandatory checks enforced in the backend.
4. **Site acceptance:** walk representative permits through the whole process with HSE and operations, including combined work, night CSE, multi-district work, shift change, failed gas test, lost calibration access, emergency stop and closure before restoration.

## Verification performed

Read-only local probes loaded the actual TypeScript functions in memory and did not call SAP:

- A future 48-hour HOT request with gas interval 8 hours and isolation required but no isolation rows is accepted as `CRTD`. This demonstrates missing request-level constraints, not field authorization.
- A safety row generated with the UI's `GENERAL` category is rejected with `Category must be at most 6 characters.`
- The gas helper reports `safe: true` for O2=20.9%, LEL=10%, H2S=10 ppm and CO=25 ppm.

Runtime UI, live SAP transition authorization, database retention and physical site practice were not tested. Full comparison against `PTW Format revision 1.docx` remains pending an accessible copy.
